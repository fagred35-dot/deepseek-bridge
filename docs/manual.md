# Дипсик Мост — полное руководство

> Короткий обзор проекта — в [README](../README.md). Здесь — подробности: все инструменты
> с примерами, API моста, флаги, коды ошибок, сборка exe и внутренности расширения.

Мост между веб-чатом [DeepSeek](https://chat.deepseek.com/) и локальной файловой системой.
Стратегия интеграции — **A: браузерное расширение**.

## Запуск моста

```bash
cd bridge
node src/server.mjs
```

Мост слушает `http://127.0.0.1:8443`, создаёт рабочую папку `~/DeepSeekWorkspace`
и открывает UI в браузере. Токен и настройки — в `~/.dsbridge/config.json`.

Переменные окружения:
- `DSBRIDGE_PORT` — порт (по умолчанию 8443; при занятости берёт следующий свободный)
- `DSBRIDGE_WORKSPACE` — рабочая папка
- `DSBRIDGE_NO_OPEN=1` — не открывать UI автоматически

## Установка расширения

1. Открой `chrome://extensions` (или `edge://extensions`).
2. Включи «Режим разработчика».
3. «Загрузить распакованное расширение» → папка `extension/`.
4. Открой UI моста, нажми «Копировать токен».
5. В расширении (иконка в панели) вставь токен → «Сохранить и проверить».

В popup видно текущую рабочую папку, её можно сменить там же: «Выбрать папку…» открывает
системный диалог, либо впиши путь руками и нажми «Применить путь». Учти: при системном
диалоге окно popup закроется (диалог забирает фокус) — папка всё равно применится, новое
значение увидишь при следующем открытии popup.

## Как пользоваться

1. Открой `https://chat.deepseek.com/` — справа снизу появится панель «Дипсик Мост».
2. Нажми «Вставить инструкцию для модели» и отправь сообщение — модель узнает о инструментах.
   Список инструментов в этой инструкции расширение забирает у моста (`/api/tools`), поэтому
   он всегда совпадает с тем, что мост реально умеет. Подробнее — [Инструкция для модели](#инструкция-для-модели).
3. Попроси, например: «прочитай файл notes.md». Модель выведет блок:

   ````dsbridge
   { "tool": "read_file", "args": { "path": "notes.md" } }
   ````

4. Панель выполнит вызов через мост и покажет карточку результата. Исходный JSON при этом
   сворачивается — вместо него компактная карточка, а кнопка «код» возвращает исходник.
5. Результат уходит в чат автоматически (галочка «авто-отправка результата»), модель
   продолжает сама.

В панели четыре настройки, они запоминаются между перезагрузками страницы:

| Галочка | По умолчанию | Что делает |
|---|---|---|
| авто-выполнение | вкл | выполнять найденные вызовы без нажатия |
| авто-отправка результата | вкл | отправлять результат в чат самому |
| прикреплять картинки в чат | вкл | скриншоты уходят модели как изображение |
| пауза между отправками | 4 с | минимальный интервал, защита от лимита DeepSeek |

### Несколько вызовов в одном сообщении

Модель может вывести подряд несколько блоков `dsbridge`. Панель собирает их в очередь,
выполняет по порядку (результаты в отдельных карточках) и отправляет **один** сводный ответ:

````dsbridge
{ "tool": "list_windows", "args": {} }
````
````dsbridge
{ "tool": "screenshot", "args": { "window": "DeepSeek" } }
````

Если один вызов зависит от результата другого (например, `screenshot` без имени окна после
`list_windows`), модель дождётся ответа и выведет следующий блок уже в следующем сообщении.

### edit_file

Главный инструмент для правок. Заменяет фрагмент, не переписывая файл целиком:

````dsbridge
{ "tool": "edit_file", "args": { "path": "src/app.js", "old_string": "const x = 1;", "new_string": "const x = 42;" } }
````

- `old_string` должна встречаться **ровно один раз** — иначе `EAMBIGUOUS` со списком номеров строк,
  где нашлось. Лечится добавлением контекста или `replace_all: true`.
- Нет совпадения → `ENOMATCH`; пустой `old_string` или `old_string === new_string` → `EARGS`.
- Пустой `new_string` удаляет фрагмент.
- Возвращает `{ replacements, firstLine, bytesBefore, bytesAfter }`.

### edit_many

Пакет правок одного файла: чтобы поправить пять мест, не нужно пять round-trip'ов через чат
(каждый — отдельная пачка «Слишком частые сообщения»).

````dsbridge
{ "tool": "edit_many", "args": { "path": "src/app.js", "edits": [
  { "old": "const x = 1;", "new": "const x = 42;" },
  { "old": "debugger;", "new": "", "replace_all": true }
] } }
````

- До 100 правок. Применяются **последовательно** к текущему состоянию текста: вторая правка
  видит результат первой, а не исходный файл.
- `atomic: true` (по умолчанию) — если хоть одна не нашлась, файл **не меняется вовсе**.
  `atomic: false` — удачные применяются, неудачные уходят в `failures`.
- Валидация: пустой `old`, `old === new`, дубликаты позиций → `EARGS`.
- Возвращает, сколько правок применилось и какие не нашлись.

Инструмент добавила сама модель через мост — вместе с тестами. Это нормальный режим работы
проекта: `allowCommands` включён, и модель правит боевые исходники.

### Переменные окружения в run_command

`env` подставляет переменные на один вызов — удобно, когда нужного инструмента нет в `PATH`:

````dsbridge
{ "tool": "run_command", "args": { "shell": "cmd", "command": "javac -version",
  "env": { "JAVA_HOME": "C:\\Program Files\\Java\\jdk-21",
           "Path": "C:\\Program Files\\Java\\jdk-21\\bin;%Path%" } } }
````

Ключи фильтруются по `[A-Za-z_][A-Za-z0-9_]*`; остальное окружение наследуется от процесса моста.
В ответе есть `envKeys` — что реально подставилось.

Значения `env` — обычные строки, а не shell-выражения, поэтому `%VAR%` и `${VAR}` мост раскрывает
сам (сначала из самого `env`, потом из окружения процесса). Именно поэтому `"%Path%"` выше
работает: `%Path%` превращается в текущий `PATH`. Если программа всё равно не находится —
`find_tool` подскажет полный путь.

### diff / diff_git

`diff { pathA, pathB }` — unified-diff двух текстовых файлов. Считается **своим** LCS-алгоритмом
(без зависимостей): возвращает `added`, `removed`, `same`, `hunks`, флаг `identical` и сам текст
диффа с ханками `@@ -a,b +c,d @@`. Для очень больших файлов (произведение строк > 4 млн) не
строит таблицу, а честно помечает всё как удалённое+добавленное.

`diff_git { path, rev }` — `git diff` по файлу: без `rev` сравнивает рабочее дерево с индексом,
с `rev` (например `HEAD~1`) — с ревизией. Это чтение, поэтому флаг «Выполнение команд» не нужен.

### find_tool

`find_tool { name }` ищет программу в `PATH` и в стандартных местах установки:
`C:\Program Files\<name>`, `C:\Program Files (x86)\<name>`, `%LOCALAPPDATA%\Programs\<name>`,
`%USERPROFILE%\.workbuddy-ai\binaries\<name>\versions\*`, а также в подпапках `bin/` и папках версий
(`jdk-21`, `22.22.2`). Возвращает список найденных путей с пометкой источника (`PATH` / `standard`).
Полезно, когда java / node / dotnet / gradle есть на машине, но не в `PATH`.

### image_info

`image_info { path }` читает заголовок картинки и отдаёт `format`, `width`, `height`, `bytes`,
`mtime` — без внешних библиотек и без полной расшифровки пикселей. Понимает png, jpeg, gif, bmp, webp.

### batch

`batch { calls: [{ tool, args }, …] }` выполняет до **50** инструментов за один вызов и возвращает
результаты **в том же порядке**. Смысл — экономия: одно сообщение в чате вместо пяти, а лимит
«Слишком частые сообщения» считает именно сообщения.

```
{ "tool": "batch", "args": { "calls": [
  { "tool": "read_file", "args": { "path": "a.txt" } },
  { "tool": "stat",     "args": { "path": "a.txt" } },
  { "tool": "grep",     "args": { "pattern": "TODO", "path": "." } }
] } }
```

По умолчанию ошибка одного вызова не мешает остальным (`stopOnError: false`): в ответе будет
`failed: 1`, а упавший элемент — `{ ok: false, error: { code, message } }`. С `stopOnError: true`
выполнение прекращается на первой ошибке (`done` меньше `count`). `batch` внутри `batch` запрещён
(`EBATCHNEST`) — иначе легко получить лавину вложенных вызовов.

Каждый под-вызов попадает в `usage_stats` отдельно, своим именем инструмента, а не как `batch`.

### Память модели: remember / recall / forget

Файл `~/.dsbridge/memory.json` — обычный ключ-значение, переживает и перезапуск моста, и
перезагрузку расширения.

- `remember { key, value, ttl? }` — сохранить. `ttl` в секундах; без него запись живёт, пока её не
  удалят. Лимит — 500 ключей, дальше `ELIMIT` с подсказкой чистить.
- `recall { key }` — точный ключ; `recall { pattern }` — подстрока или регулярка по ключу и значению;
  `recall {}` — всё, свежее сверху. Просроченные записи вычищаются при чтении, счётчик в
  `expiredRemoved`.
- `forget { key }` — удалить одну запись (`removed: false`, если её не было — это не ошибка);
  `forget { all: true }` — стереть всё.

Ответы содержат `at` (когда записано) и `expiresAt` — чтобы модель видела возраст факта.

### process_logs

`process_logs` читает то, что накопили `start_process`-процессы:

- `tail` — сколько строк с конца (по умолчанию 100, до 2000);
- `since` — вернуть только новое: передайте сюда `nextOffset` из прошлого ответа. Это может быть
  число (смещение `stdout`) или объект `{ stdout, stderr }` — у каждого потока свой курсор;
- `waitMs` — аналог `tail -f`: подождать нового вывода, вернуться сразу, как только он появится
  (или по таймауту, или когда процесс завершился). До 30 с;
- `clear` — очистить буфер процесса.

Если буфер успел обрезаться сверху, `truncated: true` — курсор сброшен, отдан весь хвост. Это
честнее, чем молча вернуть пустоту.

### usage_stats

`usage_stats { sort, limit, reset }` — что и сколько вызывалось за время жизни моста: `calls`,
`errors`, `totalMs`, `avgMs`, `maxMs`, `lastAt` по каждому инструменту, плюс `totals` и
`uptimeSec`. `sort` — `calls` | `errors` | `avg` | `max` | `total` (по умолчанию `total`).
`reset: true` обнуляет счётчики после отчёта. Удобно, чтобы найти узкое место (обычно `screenshot`
и `run_command`).

### read_around

`read_around { path, pattern, before, after }` — «курсор» по файлу: показывает N строк до и после
вхождения регулярки (по умолчанию по 20, до 500). Возвращает не только окно, но и `matches` —
сколько вхождений всего, `matchesAt` — их номера строк, и `hit` — какое по счёту взять. Один вызов
вместо «grep, потом read_lines с посчитанными руками строками».

### Кодировки и зарезервированные имена Windows

- `read_file { path, encoding: "auto" }` определяет кодировку по BOM, строгому UTF-8, а если
  не вышло — по эвристике между cp1251 и cp866 (частый случай — вывод PowerShell). Поле
  `encoding` в ответе говорит, что именно распознано.
- Имена `nul`, `con`, `aux`, `prn`, `com1-9`, `lpt1-9` Windows считает **устройствами**, а не
  файлами. Node не может ни создать, ни переименовать такой файл (`EPERM`), и префикс `\\?\`
  здесь, по проверке, не помогает. Поэтому `delete` / `move` / `copy` при таком имени пробуют
  обходной путь через PowerShell и, если не вышло, возвращают понятный `ERESERVED` вместо сырого
  `EPERM`. `stat` и `read_file` такие файлы читают штатно.

### git

````dsbridge
{ "tool": "git", "args": { "subcommand": "log", "args": ["--oneline", "-10"] } }
````

Подкоманда и её аргументы передаются **argv-массивом, без оболочки** — поэтому кириллица и
кавычки в сообщении коммита не ломаются:

````dsbridge
{ "tool": "git", "args": { "subcommand": "commit", "args": ["-m", "фикс: «Волна» не стартовала"] } }
````

- Читающие подкоманды (`status`, `diff`, `log`, `show`, `rev-parse`, `ls-files`, `blame` и др.)
  работают всегда.
- Изменяющие (`add`, `commit`, `checkout`, `push`, `merge`, `branch`, `tag`, `config` …) требуют
  `allowCommands`. Подкоманды, которые умеют и то и другое, отнесены к изменяющим: разобрать
  их аргументы надёжно нельзя.
- Аргументы `-C`, `--exec-path`, `--upload-pack`, `--receive-pack`, `--config-env` отклоняются.
- Вне репозитория инструмент не падает: возвращает `exitCode 128` и текст git в `stderr`.

### Фоновые процессы

`run_command` синхронный и убивается по таймауту, поэтому для сервера предпросмотра есть отдельная пара:

````dsbridge
{ "tool": "start_process", "args": { "command": "python -m http.server 8080", "shell": "cmd", "name": "preview" } }
````
````dsbridge
{ "tool": "list_processes", "args": {} }
````
````dsbridge
{ "tool": "kill_process", "args": { "name": "preview" } }
````

- `start_process` ждёт до 1,2 с и сообщает, если процесс умер сразу (частый случай — опечатка
  в команде). Вывод копится в кольцевом буфере, `list_processes` отдаёт хвост по 4 КБ.
- `kill_process` принимает `pid` или `name` и убивает **дерево** процессов. `taskkill /F`
  срабатывает не мгновенно, поэтому инструмент ждёт подтверждения до 3 с.
- Реестр живёт в памяти моста: после перезапуска о старых процессах ничего не известно.
- Максимум 20 одновременно; завершённые вытесняются первыми. Требует `allowCommands`.

### Сетевой доступ

`download`, `http_get`, `http_post` — **за флагом `allowNetwork`, по умолчанию выключено.**

````dsbridge
{ "tool": "download", "args": { "url": "https://example.com/logo.png", "path": "assets/logo.png" } }
````

- `download` пишет через временный файл `.part`: если сервер оборвёт соединение, на месте
  целевого файла не останется огрызка. Имя из URL выводится автоматически.
- `http_get` отдаёт текст (JSON, XML, HTML) — до 512 КБ, дальше помечает `truncated`.
  Бинарные ответы **не** тянутся в чат: возвращается `binary: true` и размер, для файла — `download`.
- Всё ограничено 25 МБ и таймаутом до 120 с. Заголовки чистятся от переводов строк.
- Без флага инструменты отвечают `EDISABLED`.

## Флаги безопасности

| Флаг | По умолчанию | Что открывает |
|---|---|---|
| `allowCommands` | `true` | `run_command`, изменяющий `git`, `start_process` / `kill_process` |
| `allowNetwork` | `false` | `download`, `http_get`, `http_post`, скриншот по http(s)-адресу |
| `extraRoots` | `[]` | доступ к папкам **вне** рабочей (по списку) |

Все три — в UI моста и поля в `POST /api/settings`. `allowCommands` включён, потому что
без него мост почти бесполезен; `allowNetwork` выключен, потому что с ним модель может отправить
содержимое твоих файлов на чужой сервер. Включай осознанно.

### Дополнительные папки (`extraRoots`)

Path jail по умолчанию пускает модель **только** внутрь рабочей папки — это правильно, но неудобно,
когда надо помочь с проектом в другом месте. `extraRoots` — список папок, которые открываются
дополнительно. Рабочая папка при этом никуда не девается.

```json
{ "workspaceRoot": "C:\\work\\site", "extraRoots": ["C:\\projects\\volna"] }
```

- Поле в UI — «Дополнительные папки»: кнопка **«Добавить папку…»** открывает системный диалог,
  текст можно вписать и руками (по одному пути на строку), затем **«Применить список»**.
- Пути нормализуются и дедуплицируются (без учёта регистра на Windows), пустые строки и мусор
  отбрасываются.
- Граница проверяется по разделителю: `C:\work\site-other` **не** считается частью `C:\work\site`.
- Вверх от дополнительной папки доступа нет — она сама становится корнем, а не «дыркой» в дерево.
- В ответах инструментов путь **вне** рабочей папки отдаётся абсолютным (`C:/projects/volna/src/app.js`),
  а не через `../../..`, чтобы модель не путалась.
- `extraRoots: []` — поведение ровно как раньше, ничего не расширяется.

Зачем это нужно: `wishlist.txt`, который модель написала сама, начинался именно с этого пункта —
она не могла помочь с проектом за пределами рабочей папки.

## Картинки и ссылки на файлы в ответе

Модель может не просто назвать файл, а показать его. Два дополнительных блока:

**Ссылка на файл** — карточка с кнопками «открыть» (в системном приложении) и «скачать»:

````dsbridge-file
{ "path": "report.md", "label": "Отчёт" }
````

**Картинка** — `src` может быть локальным путём (относительно рабочей папки) или ссылкой http(s):

````dsbridge-image
{ "src": "screenshots/shot-1.png", "alt": "Скриншот окна" }
````

Локальные картинки расширение забирает через `/api/raw` и вставляет как `data:URL` — это
обходит и mixed-content, и CSP страницы. Ссылки из интернета подставляются напрямую; если
CSP чата их заблокирует, появится ссылка «открыть картинку в новой вкладке».

Типовой сценарий «сделай скриншот окна»:

````dsbridge
{ "tool": "screenshot", "args": { "window": "Visual Studio Code", "path": "shots/vscode.png" } }
````
````dsbridge-image
{ "src": "shots/vscode.png", "alt": "VS Code" }
````

## Скриншот веб-страницы

Тот же инструмент, но с `url` — рендерит страницу в headless-браузере. **Это даёт модели
обратную связь по вёрстке:** она собирает html, смотрит на результат и правит, а не пишет вслепую.

````dsbridge
{ "tool": "screenshot", "args": { "url": "site/index.html", "width": 1280, "height": 900 } }
````
````dsbridge-image
{ "src": "screenshots/page-1.png", "alt": "Как выглядит страница" }
````

- `url` — **локальный файл рабочей папки** (сеть не нужна) либо `http(s)`-адрес
  (тогда требуется `allowNetwork`).
- `width` / `height` — размер вьюпорта (320–3840 и 240–12000), по умолчанию 1280×900.
  Прежний потолок 2160 снят: длинную страницу теперь можно снять одним кадром.
- `fullPage: true` — высокий кадр «всей страницы» (минимум 6000 px по высоте). Это **приближение**:
  без CDP Chrome не сообщает высоту документа, поэтому берётся заведомо большой кадр.
- `device: mobile | tablet | desktop` — типовой размер окна плюс мобильный User-Agent.
- `dark: true` — тёмная тема браузера (`--force-dark-mode`).
- `waitMs` — сколько «прокрутить» время для отрисовки, по умолчанию 3000 мс. Это
  `--virtual-time-budget`, поэтому страница успевает выполнить JS и догрузить картинки.
- Браузер берётся установленный: Chrome, Edge, Chromium, Brave. Своего мост не тащит.
  Если не нашёлся — путь можно задать в `DSBRIDGE_BROWSER`.
- Каждый запуск идёт со **своим временным профилем**: с профилем по умолчанию уже
  запущенный Chrome просто открыл бы вкладку в существующем окне и проигнорировал headless.
- Возвращает `{ path, bytes, mode: page-local | page-remote, width, height, browser, fullPage, dark, device }`.
- **Повторный снимок в тот же путь перезаписывает файл** — это и есть цикл «поправил →
  снял заново». Перед запуском браузера старый файл не удаляется: удаление — лишняя точка
  отказа (файл может быть занят или закрыт правами), а Chrome и так пишет поверх. Вместо
  этого запоминается время изменения, и если после запуска файл не обновился — инструмент
  честно вернёт `ESHOT`, а не старую картинку.

## Зрение: модель видит скриншоты

Главная проблема первой версии: `dsbridge-image` показывает картинку **пользователю**, а модель
получает только путь и размер. Она пишет «вижу, что карточки ровные», глядя на собственный код,
а не на результат. Это не помощь, а имитация.

Решение — расширение само прикрепляет файл к следующему сообщению. DeepSeek загружает его как
обычное вложение, и модель получает картинку мультимодально.

```
screenshot → файл png в рабочей папке
           → расширение читает его через /api/raw
           → подставляет File в input[type=file] чата
           → картинка уходит вместе с результатом инструмента
```

- Работает автоматически после `screenshot` и на каждый блок `dsbridge-image`
  с локальным путём (внешние `http(s)` не трогаются — их может не быть в доступе).
- Один и тот же файл не прикрепляется дважды в течение минуты.
- Перед отправкой расширение **дожидается загрузки вложения**: пока картинка грузится,
  кнопка отправки отключена, и сообщение ушло бы без неё.
- Если `input[type=file]` на странице не нашёлся, есть запасной путь через `drag&drop`.
  Кликать по кнопке «прикрепить» нельзя — она открывает системный диалог выбора файла,
  который перехватывает фокус.
- Выключается галочкой **«прикреплять картинки в чат»** в панели.
- На карточке результата есть кнопка «Прикрепить картинку в чат» — на случай, если
  автосрабатывание не сработало.

## Пауза между отправками

DeepSeek отвечает «Слишком частые сообщения. Повторите попытку позже», если писать слишком
часто, и потом приходится ждать вслепую. Отправка идёт через шлюз:

- **Минимальный интервал** между сообщениями — поле «пауза между отправками» в панели,
  по умолчанию 4 с, хранится в `chrome.storage.local` (переживает перезагрузку страницы).
- **Ожидание конца генерации.** Пока модель отвечает, на месте кнопки отправки стоит «стоп»,
  и клик по ней оборвал бы ответ. Расширение ждёт до 20 с, потом отправляет как есть.
- **Штрафная пауза за лимит.** Текст ошибки ищется на странице; если он появился именно
  после нашей отправки, включается пауза 10 с → 20 → 40 → 80 → 120 с (потолок). Успешная
  отправка сбрасывает счётчик. Текущее состояние видно строкой под настройками.

Сравнивается **число** вхождений текста до и после отправки, а не «есть/нет»: старое
сообщение об ошибке висит в чате и иначе принимало бы каждую удачную отправку за провал.

## Инструкция для модели

Кнопка «Вставить инструкцию для модели» кладёт в поле ввода большой текст, который объясняет
модели, как вызывать инструменты. Он собран из трёх частей:

1. **Проза до списка** — формат вызова, сколько вызовов за сообщение, как «увидеть» результат
   (зрение), правила про `dsbridge-file` / `dsbridge-image`.
2. **Список инструментов** — собирается **из ответа моста** `/api/tools` на момент нажатия
   кнопки. Расширение проходит по группам из `TOOL_GROUPS` (`extension/content.js`), берёт для
   каждого инструмента имя, имена аргументов и описание из реестра `TOOLS`.
3. **Проза после списка** — таблица «вместо `run_command` лучше…», что не делать молча,
   особенности Windows, флаги моста, коды ошибок, память между чатами, рабочие процессы.

Почему список генерируется, а не написан руками: раньше он дублировался в промте и **отставал
от кода** — новые инструменты в инструкции просто не появлялись, и модель про них не знала.
Теперь добавил инструмент в `bridge/src/tools.mjs` — он сам появился в промте.

Группы — только для читаемости. Инструмент, которого нет ни в одной группе, попадает в раздел
«Прочее», поэтому потеряться он не может. Это закреплено тестом: `extension/test.mjs`
импортирует настоящий `TOOLS` из моста и сверяет с ним собранный список — если инструмент
не доедет до промта, тест упадёт.

Если мост не ответил (не запущен, порт занят), инструкция всё равно вставляется — но со
списком **только из имён** инструментов и пометкой, что подробности недоступны.

## API моста

| Метод | Путь | Auth | Назначение |
|---|---|---|---|
| GET | `/api/health` | — | статус, версия, рабочая папка, `allowCommands`, `allowNetwork`, `extraRoots`, список инструментов |
| GET | `/api/tools` | токен | список инструментов с описанием (`tools` + `external` от внешних MCP) |
| POST | `/api/tool` | токен | выполнить инструмент (включая внешние `<server>__<tool>`) |
| POST | `/mcp` | токен | MCP-эндпоинт: JSON-RPC 2.0, Streamable HTTP |
| GET | `/api/mcp/status` | токен | статус подключённых внешних MCP-серверов |
| GET | `/api/raw` | токен | отдать файл из рабочей папки (`path`, `download`) |
| POST | `/api/open-file` | токен | открыть файл системным приложением |
| POST | `/api/pick-folder` | токен | системный диалог выбора папки |
| POST | `/api/settings` | токен | `workspaceRoot` / `allowCommands` / `allowNetwork` / `extraRoots` |
| GET | `/api/events` | токен | SSE-поток событий |
| POST | `/api/open` | токен | открыть папку в проводнике |

Токен передаётся в заголовке `X-Bridge-Token` или параметром `?token=` (для SSE и для
`<img src>`, где заголовок задать нельзя).

Пример:
```bash
curl -s http://127.0.0.1:8443/api/tool \
  -H "X-Bridge-Token: <token>" -H "Content-Type: application/json" \
  -d '{"tool":"list_dir","args":{"path":"."}}'
```

## Тесты

```bash
cd bridge
node test.mjs
```

197 проверок: все инструменты, path jail и `extraRoots`, авторизация, `/api/raw`,
`/api/open-file`, смена рабочей папки, SSE. Отдельные группы — `diff` / `diff_git`,
`image_info`, `find_tool`, распознавание кодировки (`read_file` с `auto` на cp1251-байтах),
`edit_many dry_run`, `list_dir recursive + glob`, `write_file createDirs:false`, раскрытие
`%VAR%` в `env`, `read_around`, `batch` (порядок, `failed`, `stopOnError`, запрет вложенности),
`remember` / `recall` / `forget` с `ttl`, `usage_stats` и `process_logs` (`nextOffset`, `clear`).
Тест поднимает отдельный сервер на порту 8471
с изолированной рабочей папкой `.test-workspace` и отдельным `DSBRIDGE_DATA=.test-data` —
**боевой `~/.dsbridge/config.json` и токен не трогаются**.

Проверки `extraRoots` идут на фикстурах `.test-extra` и `.test-extra-other`. Соседняя папка
с похожим именем — это отдельный кейс: она должна остаться закрытой, иначе граница
«по префиксу» пропустила бы всё, что начинается с того же текста.

Сетевые инструменты проверяются на **локальном** HTTP-сервере внутри теста (порт 8472):
в интернет ничего не уходит, результат детерминирован. Проверяются в том числе реальное
скачивание PNG с побайтовым сравнением хеша, отказ при 404 и отсутствие мусорных `.part`
файлов после неудачи. git-тесты работают в отдельном репозитории внутри `.test-workspace`
и задают локальные `user.name` / `user.email`, чтобы не зависеть от настроек машины.

Скриншот веб-страницы проверяется на локальном html: файл читается обратно и сверяется
магия PNG. Отдельно проверяется **перезапись того же пути** (цикл «поправил → снял заново»)
и что чужой файл на месте цели не переживает снимок. Проверки скриншотов окна и экрана
требуют активной десктопной сессии (в headless-окружении упадут).

### Тесты расширения

```bash
cd extension
node test.mjs
```

49 проверок: разбор `data:URL` в `File` (включая побайтовое сравнение сигнатуры PNG),
выделение имени файла из пути, подсчёт срабатываний лимита и рост штрафной паузы, а также

`content.js` — это IIFE, живущий в DOM страницы, целиком в Node его не запустить. Поэтому
тест **вычитывает тела функций из самого `content.js`** и исполняет их в песочнице. Копия
кода в тесте разошлась бы с боевой и перестала что-либо доказывать.

## Сборка в один exe

```bash
cd bridge
node build.mjs
# → dist/dsbridge.exe  (~83 МБ, внутри рантайм и весь код)
```

Требуется Node ≥ 20 и `npx` (для postject).

Что происходит по шагам:

1. **Бандл.** SEA принимает ровно один **CommonJS**-скрипт, а исходники — ESM в девяти модулях,
   поэтому `build.mjs` склеивает `src/*.mjs` в один `dist/bundle.cjs` своим мини-бандлером
   (~80 строк: `import … from`, побочные `import`, `export const|let|var|function|class`,
   `import.meta.url`). На неподдерживаемом экспорте сборка падает, а не собирает молча сломанный файл.
2. **Внешние файлы.** `public/index.html` вшивается строкой, а `scripts/screenshot.ps1`
   распаковывается в `os.tmpdir()` при первом обращении — его нельзя вшить, он запускается как файл.
   Оба берутся через `src/assets.mjs`: сборка подменяет исходник этого модуля целиком, поэтому
   остальной код о режиме запуска не знает.
3. **SEA + postject.** `node --experimental-sea-config`, копия `node.exe`, инъекция блоба.
   `warning: The signature seems corrupted!` от postject — **это норма**, официальный node.exe подписан.
4. **Самопроверка.** Сборка копирует exe в чистую временную папку, запускает без файлов проекта
   и дёргает живые эндпоинты: `/api/health`, `GET /` (вшитый html + подстановка токена),
   `write_file`/`read_file`, `sysinfo`, `list_windows` (он и доказывает, что `screenshot.ps1`
   распаковывается). Любой провал — `exit 1` с разбором. Пропустить: `node build.mjs --no-verify`.

«Сборка прошла успешно» здесь ничего не значит: ошибки бандлинга видны **только на запущенном
exe**, поэтому проверка встроена в сборку, а не делается руками.

Если exe уже запущен, копирование `node.exe` упадёт с `EBUSY` — сборка скажет об этом прямо.
Отдельно: exe и `node src/server.mjs` делят один конфиг `~/.dsbridge/config.json`, так что
запущенный экземпляр занимает порт; второй поднимется на следующем свободном, и расширение,
настроенное на прежний порт, его не найдёт.

```bash
# запустить собранный exe, не открывая браузер
DSBRIDGE_NO_OPEN=1 ./dist/dsbridge.exe
```

## Выполнение команд (run_command)

Инструмент запускает команды от твоего имени в рабочей папке:

````dsbridge
{ "tool": "run_command", "args": { "shell": "powershell", "command": "Get-ChildItem" } }
````

- `shell`: `powershell` (по умолчанию), `pwsh`, `cmd`, `bash`.
- `cwd`: подпапка рабочей папки (path jail действует).
- `timeoutMs`: 1–120 с, по умолчанию 30 с; по таймауту дерево процессов убивается.
- Возвращает `{ exitCode, stdout, stderr, timedOut, durationMs }`, вывод обрезается до 64 КБ на поток.
- Кириллица: PowerShell запускается через `-EncodedCommand` (UTF-16LE → base64), cmd — через
  временный `.cmd` в UTF-8. Кодировки не ломаются.

**Выключить:** чекбокс «Разрешить run_command» в UI моста (пишется в `config.json` как
`allowCommands`). При выключенном флаге инструмент отвечает `EDISABLED`.

## Безопасность

- Мост слушает только `127.0.0.1` и требует токен на каждую операцию.
- Все пути ограничены рабочей папкой (path jail); выход за её пределы → `EPATHJAIL`.
  Единственное исключение — папки из `extraRoots`, и только они: список задаёшь ты, по умолчанию пуст.
- `delete` не удаляет, а переносит в `<workspace>/.trash`.
- Каждый вызов пишется в `~/.dsbridge/audit.log`.
- `run_command` — самый опасный инструмент: это исполнение произвольных команд от твоего имени.
  Модель видит текст веб-страницы, поэтому теоретически возможна prompt-injection. Держи
  `allowCommands` выключенным, когда он не нужен.

### Известная шероховатость

**PowerShell 5.1 и вывод .exe.** Конструкция `& 'C:\...\java.exe' -version | Out-String` падает
с `CantActivateDocumentInPipeline`, потому что java пишет версию в stderr, а PowerShell трактует
это как поток ошибок. Обход — `2>&1 | Out-String` либо `cmd /c`. `run_command` тут ни при чём:
он возвращает `stdout` и `stderr` раздельно.

**CLIXML в stderr.** При `-EncodedCommand` с перенаправленным stderr PowerShell отдаёт ошибки
не текстом, а XML-сериализацией: `#< CLIXML <Objs...><S S="Error">текст</S>`. Мост разбирает
её обратно в читаемый текст (`decodeClixml` в `shell.mjs`). Флаг `-OutputFormat Text` этого
**не** лечит — проверено. Отказаться от `-EncodedCommand` нельзя: именно он сохраняет
кириллицу и кавычки.

**Чужой перехватчик `fs` ломает скриншоты.** Если мост запущен из окружения, которое
подменяет `fs.rmSync` (песочница, корзина-обёртка, антивирусный шим), массовые удаления
начинают падать. `screenshot` каждый раз чистит временный профиль Chrome — это около
480 файлов, и на них легко упереться в лимит. Симптом — ошибка вида
`[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]` с полем `count` в разы больше
`threshold`. Лечится запуском моста из обычной консоли, без наследованных переменных
окружения вроде `NODE_OPTIONS`.
