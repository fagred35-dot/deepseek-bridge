1.1. Зарезервированные имена Windows (S)

Файл с именем nul (и con, aux, prn, com1-9, lpt1-9) НЕ удаляется
штатным путём: delete возвращает EPERM, потому что Windows
считает это именем устройства, а не файла.

Я наткнулся на такой файл в проекте CrosshairOverlay — он остался
от чьей-то неудачной bash-команды (nul вместо /dev/null). Убрать
его не смог ни delete, ни move.

Решение: в delete/move/copy/stat — если basename совпадает с
зарезервированным именем, использовать префикс \\?\ (Win32
long path API) для обхода.

Тесты: создать файл nul (через echo > \\?\C:\...\nul),
проверить, что delete уносит его в .trash.

1.2. Автопоиск инструментов при CommandNotFoundException (M)

java, node, dotnet, gradle, cmd, python — установлены, но НЕ в PATH.
Каждый раз трачу вызовы на выяснение полного пути и Start-Process.

Идея: при CommandNotFoundException в run_command — автоматически
поискать в стандартных местах установки:
- C:\Program Files\<name>\
- C:\Program Files (x86)\<name>\
- %LOCALAPPDATA%\Programs\<name>\
- C:\Users\<user>\.workbuddy-ai\binaries\<name>\versions\*\

Или проще: новый инструмент find_tool { name } -> путь или список
путей. Полезно для диагностики окружения.

1.3. encoding_detect / read с кодировкой (S)

Файл nul при чтении отдал кракозябры — это был текст PowerShell
в cp866, а read_file читает как UTF-8. Не критично, но мешает.

Идея:
- read_file { path, encoding? } — явно указать кодировку
- read_file { path, encoding: "auto" } — определить по BOM /
  эвристике (UTF-8 valid? нет — cp1251/cp866?)
- Отдавать в ответе detectedEncoding, чтобы модель знала

1.4. edit_many { dry_run: true } (S)

Показать, что БУДЕТ изменено, без записи на диск. Полезно перед
крупной правкой: убедиться, что old найден в нужном месте.

Возврат: какие правки найдут цель, какие ENOMATCH, какие
EAMBIGUOUS, сколько вхождений. Файл не трогается.

1.5. README для моделей: явно про «зрение» (S)

Я нашёл, что dsbridge-image прикрепляет картинку к чату, только

1.6. %Path% не раскрывается в env (S, документация)

run_command { env: { "Path": "C:\\java\\bin;%Path%" } } —
%Path% остаётся буквально, как строка, и PATH не наследуется.
Потому что env — это объект, а не shell-строка.

Либо реализовать раскрытие %VAR% / ${VAR} в env,
либо явно написать в README, что %Path% не работает, и надо
указывать полный PATH руками.

1.7. EBRIDGE / «Extension context invalidated» в README (S)

Во время пересборки моста вызовы молча теряются — связь рвётся,
ответ не приходит. Я принял это за «лимит шагов», пока не проверил.

Написать в README для моделей: при EBRIDGE — файлы на диске целы,
мост перезапускается (например, при обновлении расширения),
подожди и повтори вызов.

ЧАСТЬ 3. НЕОЧЕВИДНОЕ, но полезное
=========================================================

3.1. Cursor-режим чтения файла (M)

Сейчас read_lines требует start/count. Хочу читать «вокруг
паттерна»: показать N строк до и после строки, где встретился
regex. По сути grep + context, но по одному файлу и с возвратом
широкого куска. Иногда удобнее, чем несколько вызовов.

3.2. list_dir { recursive: true, maxDepth, glob } (S)

list_dir сейчас один уровень. tree даёт визуальное дерево, но
неудобен для программной обработки. Хочу плоский список
с фильтрами.

3.3. write_file { createDirs: true } (уже есть?) (S)

Сейчас write_file делает mkdir -p, если папки нет — это правильно.
Но иногда наоборот: хочу ошибку, если папки нет (защита от опечатки
в пути). Опция createDirs: false.

3.4. Пакетная проверка: 
     batch { calls: [{tool, args}, ...] } (M)

Один round-trip — несколько инструментов. Расширение уже умеет
выполнять несколько блоков dsbridge подряд, но каждый блок —
отдельный вызов в чате. Если бы был batch — экономия на лимитах
«Слишком частые сообщения».

Пример:
  batch { calls: [
    {tool: "read_file", args: {path: "a.txt"}},
    {tool: "read_file", args: {path: "b.txt"}},
    {tool: "grep", args: {pattern: "TODO", path: "."}}
  ]}
Возврат: массив результатов в том же порядке.

3.5. Метрики вызовов (S)

Для оптимизации: сколько времени занял каждый инструмент, сколько
раз вызывался за сессию. Может пригодиться, чтобы понять, где
узкие места (например, screenshot долгий).

Новый инструмент: usage_stats -> топ инструментов по времени/частоте.

3.6. Screenshot с превью (S)

screenshot уже сохраняет PNG. Хорошо бы возвращать ещё и маленькое
ASCII-превью или доминирующий цвет — для быстрой диагностики,
если картинку не видно. Дублирует image_info, но встроено в screenshot.
