## 25.09.2026 — персонажи и скиллы (пункт 4 wishlist)

**Задача.** Кастомные персонажи и скиллы — «если позиционировать продукт как рабочую
станцию». В wishlist это помечено как низкий приоритет, потому что для моста
инструментов не критично. Сделали то, что реально полезно, а не просто UX-надстройку.

**Персонажи.** Сохраняемый system-промпт с именем: «Python-разработчик»,
«Редактор строгих текстов». Пользователь выбирает его в popup, и текст подмешивается

клиенты видят их как слэш-команды. Пользователь один раз описал workflow, и он
воспроизводится, а модели не нужно угадывать последовательность шагов.

**Инструменты (9 новых).** `persona_list/get/set/delete`, `skill_list/get/set/delete`,
`skill_render`. Плюс MCP: `prompts/list`, `prompts/get`, capability `prompts` в

## 25.09.2026 — инструмент python вместо Pyodide (пункт 3 wishlist)

**Задача из wishlist.** «Python-раннер через Pyodide — для лёгких скриптов без
Node.js-процесса, как fallback, когда мост недоступен».

**Почему Pyodide не взяли.** Проверка показала: на машине уже стоит нативный
**Python 3.11.9** в PATH. Pyodide — это Python в WASM, работающий в браузере, с
виртуальной ФС: он не видит файлы пользователя, не импортирует установленные
пакеты, и без моста всё равно бесполезен. Единственная его ценность — «Python без
установки», а он установлен. Тащить 10 МБ WASM и второй рантайм ради дубля — плохая
сделка. Сделали полезное вместо буквального.

**Что сделано — инструмент `python`** в мосте поверх нативного интерпретатора:

```json
{ "tool": "python", "args": { "code": "print(open('data.txt').read())" } }
```

Модель присылает **код**, а не команду с shell-экранированием. Это убирает главную
боль `run_command` на Windows: кавычки, пайпы, `%VAR%`, «пайп даёт пустой stdout».

Параметры: `code` (обязательный), `cwd`, `timeoutMs`, `args` (→ `sys.argv[1:]`),
`stdin`. Интерпретатор ищется тем же механизмом, что `find_tool`: PATH, потом
стандартные места; на Windows пробуются `python`, `py`, `python3`.

**`runProcess` научился stdin.** Раньше его не было — скрипт с `input()` висел бы
до таймаута. Теперь переданная строка пишется в поток и поток закрывается.

**Грабли, которые поймал тест.** Python на Windows пишет в cp1251/cp866, а мост
читает stdout как UTF-8 — кириллица превращалась в мусор. Лечится переменными
`PYTHONUTF8=1` и `PYTHONIOENCODING=utf-8` при запуске.

**Чем проверено.** `bridge/scripts/python-smoke.mjs` — **7 ok**: простой скрипт,
stderr и код возврата, `sys.argv`, stdin, запись файла в рабочей папке, исключение
с трассировкой, пустой `code` → EARGS. Штатный набор: `bridge/test.mjs` —
**248 ok / 0 fail** (было 240, +8 проверок python). Инструментов в реестре: 40 → 41.

## 24.09.2026 — XML-теги как альтернатива JSON (пункт 2 wishlist)

**Задача.** JSON в dsbridge-блоке хрупкий: модели путают запятые и кавычки.
Теги проще и для генерации, и для разбора. Сделать гибрид: старый формат работает,
новый добавляется.

**Формат.** Имя инструмента — в атрибуте `name`, каждый аргумент — отдельный тег:

```dsbridge
<dsbridge-tool name="edit_file">
  <path>src/app.js</path>
  <old_string>было</old_string>
  <new_string>стало</new_string>
</dsbridge-tool>
```

Ссылка на файл и картинка — то же самое:
`<dsbridge-file path="report.md" label="Отчёт"/>`,
`<dsbridge-image src="shot.png" alt="Скриншот"/>`.

**Что умеет разбор.** Раскрывает `&lt; &gt; &amp; &quot; &#39;`. Приводит типы:
целые и дробные → number, `true`/`false` → boolean, `null` → null, JSON-массив или
объект в теле тега → структура. Многострочные значения сохраняются как есть.

**Обратная совместимость — главное.** `classify` сначала пробует JSON, и только
если он не вышел — теги. Оба формата дают **один и тот же spec**, поэтому дальше по
коду разницы нет: ни дедупликация, ни карточки, ни очередь не знают, чем был вызов.
Тест это проверяет сравнением `JSON.stringify` двух spec-ов.

**Инструкция для модели** дополнена примерами тегов — рядом с JSON, не вместо него.

**Чем проверено.** `extension/test-xml.mjs` — **34 ok / 0 fail**: разбор основного
формата, приведение типов, JSON внутри тега, экранирование, многострочность,
устойчивость к мусору, файл/картинка, и главное — равенство spec-ов JSON и XML.
`extension/test.mjs` — **114 ok / 0 fail**, `extension/test-inject.mjs` — **22 ok**.

## 24.09.2026 — MCP как второй транспорт: мост и сервер, и клиент

**Задача (wishlist от Brick'а).** «Прикрути к мосту поддержку MCP, как локальных, так и
нет — чтобы ты мог вызывать инструменты». Плюс отдельно: подключить
`github.com/domdomegg/computer-use-mcp` и посмотреть, как он работает.

**Что сделано — два направления сразу.**

1. **Мост = MCP-сервер.** `bridge/src/mcp.mjs` — JSON-RPC 2.0 поверх Streamable HTTP.
   Эндпоинт `POST /mcp` отдаёт те же 40 инструментов, что и `/api/tool`, но по протоколу
   MCP: `initialize`, `tools/list`, `tools/call`, `ping`, уведомления. Значит мост можно
   подключить к Claude Desktop, Cursor, VS Code и любому другому MCP-клиенту — без
   расширения и без JSON-блоков в чате.

2. **Мост = MCP-клиент.** `bridge/src/mcp-client.mjs` — мост подключается к ВНЕШНИМ
   MCP-серверам и проксирует их инструменты в общий список. Два транспорта: `stdio`
   (локальный процесс, например `npx -y computer-use-mcp`) и `http` (удалённый сервер).
   Инструменты внешнего сервера появляются под именем `<server>__<tool>` и доступны
   ОБОИМИ транспортами — и через `/mcp`, и через `/api/tool` из расширения.

**Почему так, а не «встроить computer-use-mcp в мост».** Внешние MCP-серверы — это
плагины: они живут своими процессами, падают и обновляются независимо. Мост остаётся
ядром, а список инструментов собирается из родных + подключённых. Это ровно та идея
«MCP как первоклассный гражданин»: dsbridge — один из транспортов, а не единственный.

**Конфиг.** В `~/.dsbridge/config.json` появилось поле `mcpServers`:
`[{ name, transport: 'stdio'|'http', command?, args?, url?, env?, enabled? }]`.
Пустой список — поведение как раньше.

**Безопасность.** `/mcp` живёт на loopback, требует тот же токен (принимает
`X-Bridge-Token`, `?token=` и `Authorization: Bearer`) и проверяет `Origin` — защита от
DNS rebinding, как требует спецификация. Ошибка инструмента отдаётся как `isError: true`
внутри результата, а не как ошибка JSON-RPC: клиент показывает её модели, а не считает
транспорт сломанным.

**Tool Sets.** У каждого инструмента в `tools/list` есть `_meta.toolSet` (files, shell,
git, screen, memory, meta, net). `tools/list` умеет фильтровать по набору — заготовка
под будущий UI «включить/выключить целую группу».

**Грабли, которые поймали по дороге.**

- `edit_many` дважды отбил правки с `EARGS: old не может быть пустой` на валидных
  фрагментах — в этой сессии надёжнее оказался `edit_file` по одной правке.
- Фейковый stdio-сервер в тесте падал `SyntaxError: Invalid or unexpected token`:
  при генерации файла через мост `\n` внутри шаблонной строки стал реальным переносом.
  Урок: в теле, которое пишется как данные, экранируй переводы строк явно.
- `spawn` на Windows с `shell: true` режет путь по пробелу (`C:\Program Files\...`).
  Флаг нужен только для `.cmd`/`.bat` (npx, npm); для `.exe` он вреден.
- Гонка рукопожатия MCP-клиента: `alive=true` сразу после `spawn` ещё не значит, что
  `initialize` и `tools/list` прошли. Разделили флаги: `alive` (процесс жив) и `ready`
  (рукопожатие завершено, список инструментов получен).

**Чем проверено.**

## 21.09.2026 — прокрутка вверх больше не выполняет старые команды

**Симптом от Brick'а:** «если прокрутить чат выше, то старые команды снова срабатывают».

**Причина.** Чат перерисовывает старые сообщения при прокрутке: узлы создаются заново, и метка
`data-dsb-done` вместе с ними пропадает. От повтора спасало только окно дедупликации в 5 секунд —
и через минуту прокрутка запускала старые команды заново, вплоть до `write_file` и `delete`.

**Починка — счётчик вместо окна по времени.** Теперь помним, сколько раз каждый вызов уже
выполнен, и сравниваем с тем, какой по счёту этот блок в текущем DOM. N-й блок с такой сигнатурой
выполняется, только если предыдущие N−1 уже были выполнены:

- перерисовка старого сообщения даёт тот же счётчик → повтор не проходит;
- новое сообщение с тем же вызовом (модель перечитывает файл после правки) даёт счётчик на
  единицу больше → выполняется, как и раньше.

На месте пропущенного повтора рисуется компактная пометка «вызов уже выполнен — повтор пропущен»
с кнопкой **«выполнить всё равно»**. Отличить перерисовку от законного повтора по DOM нельзя
(виртуализация ленты стирает старые сообщения), поэтому выбор отдан человеку, а не угадыванию.

**Попутно найден и починён второй баг — двойное выполнение одного блока.** `candidateNodes()`
возвращал один и тот же блок несколько раз: как `<pre>` и как его `<code>`, а у разметки вроде
Qwen — как контейнер, его содержимое и строку внутри. От двойного запуска спасало всё то же окно
в 5 секунд. Теперь блок попадает в список один раз: вложенные узлы отбрасываются, а приоритет
отдан `<code>` (он несёт класс языка, который нужен разбору).

**Мелочи для устойчивости:**

- Сигнатура вызова считается по **устойчивой сериализации** аргументов: `{"tool":…,"args":…}` и
  `{"args":…,"tool":…}` — один и тот же вызов, а обычный `JSON.stringify` давал разные строки.
- Разбор блока кэшируется по тексту узла — нумерация требует знать сигнатуру и у уже
  обработанных блоков, а парсить один и тот же JSON на каждом проходе незачем.
- В диагностике панели появился счётчик **«повторов: N»**.

**Чем проверено.** Дымовой тест в настоящем Chrome расширен до трёх фаз и проверяет именно
поведение ленты:

1. обычная работа — каждый вызов выполняется ровно один раз;
2. **имитация прокрутки вверх** — лента перерисовывается с нуля (метки и карточки пропадают,
   блоки снова выглядят сырым JSON): вызовы НЕ выполняются повторно, в чат ничего не уходит,
   на месте блоков появляются пометки;
3. **новое сообщение с тем же вызовом** — выполняется, то есть законные повторы не сломаны.

Смоук — **24 ok / 0 fail**. Он переехал в репозиторий: `extension/smoke/` (запуск
`node extension/smoke/run.mjs`, подмена проверяемого файла — `DSB_CONTENT=<файл>`). Проверено,
что тест ловит баг: с отключённой дедупликацией он падает на фазе 2 («было 1, стало 2», и
второй клик по кнопке отправки) — 16 ok / 8 fail.

`extension/test.mjs` — **114 ok / 0 fail** (было 105): добавлены проверки сигнатуры вызова и
устойчивой сериализации аргументов. `bridge/test.mjs` — 214 ok / 0 fail. Версия расширения —

## 21.09.2026 — адаптеры проверены на живых сайтах, три промаха починены

**Главное:** научился снимать настоящий DOM чужих чатов (headless Chrome + CDP) и прогонять
на нём **функции прямо из `content.js`** — без переписывания. Проверил 8 сайтов, нашёл три
промаха в общем пути и починил их. Плюс нашлась и починена **главная причина «на Qwen и Z.ai
не работает»** — разбор блока кода был слишком строгим.

### Как проверялось

- Chrome поднимается headless с `--remote-debugging-port`, страница навигируется, а в неё
  через `Runtime.evaluate` отправляется код, собранный из **исходника** `content.js`
  (функции вырезаются регулярками — тот же приём, что в `extension/test.mjs`).
- Проверялось не «нашёлся ли элемент», а весь путь: какой узел выбран как поле ввода, влез ли
  в него текст (`value`/`textContent` после вставки), какая кнопка выбрана как отправка и
  сколько миллисекунд понадобилось, чтобы она стала нажимаемой.
- Отдельно проверялись ложные срабатывания: `isGenerating()` и `rateLimitHits()` на живой
  странице. Ложное «модель ещё пишет» или ложный лимит дают не поломку, а вечные паузы —
  и выглядят как «ничего не работает». На проверенных сайтах ложных срабатываний нет.

### Что нашлось и починено

- **AI Studio:** общий путь выбирал кнопкой отправки `button.carousel-nav__btn` — стрелку
  карусели в другом конце страницы. Кнопки Run в композере нет, пока поле пустое, зато
  кнопок-иконок на лендинге десятки.
- **MiniMax:** кнопка отправки — **не `<button>`, а `div[role=button]`** с
  `data-testid="send-button"`. Общие селекторы были привязаны к тегу `button` и её не видели,
  а запасной путь выбирал кнопку бокового меню.
- **Общая причина обоих промахов:** запасное правило «последняя кнопка-иконка на странице».
  Иконка без подписи ничего не доказывает — таких кнопок на любом чате десятки.
  Теперь учитываются только иконки **рядом с полем ввода** (`gapToInput` + порог 240 px).
  Ничего рядом — лучше не нажать ничего, чем нажать что попало.
- Общие селекторы отправки перестали быть привязанными к тегу: элемент с
  `data-testid="send-button"` или с подписью «Send message» — это отправка по определению,
  чем бы он ни был в разметке. Исключение — `button[type="submit"]`, он бывает только у кнопки.

### Разбор блока: JSON вырезается из текста (главная причина «не работает»)

Поводом стал вопрос Brick'а: «в Qwen не работает, в Z.ai тоже не работает». Проверка показала,
что поле ввода и кнопка отправки на обоих сайтах находятся правильно, а сообщение уходит — значит
обрыв дальше. Дальше — это разбор ответа модели.

Причина оказалась в двух строках. Разбор требовал, чтобы **весь** текст блока кода был JSON:

```js
const t = normalize(codeEl.textContent);
if (!t.startsWith("{")) return null;      // ← здесь
json = JSON.parse(t);                      // ← и здесь
```

У Qwen и Z.ai в контейнер блока кода попадает ещё и подпись языка, и кнопка «копировать». Любая
из них — и блок молча пропускался: ни вызова, ни ошибки, ни строчки в логе. Снаружи это выглядит
ровно как «модель не отвечает блоками».

Теперь JSON **вырезается из текста** — берётся первая `{` и идёт до парной закрывающей скобки,
с честным отслеживанием строк и экранирования (иначе `}` внутри строки обрывал бы объект на
середине). Замер на одном и том же тексте: старый разбор брал 1 блок из 4, новый — 4 из 4.

Заодно дешёвая отсечка в `scan()` сменилась с `startsWith("{")` на `includes("{")`, иначе блок
не доходил даже до разбора.

**Диагностика стала отвечать на вопрос «модель не написала блок или мы его не увидели»:** кнопка
«DOM» теперь печатает, сколько на странице блоков кода, сколько из них с JSON, сколько распознано
вызовов и сколько блоков вообще упоминают `dsbridge`. Если упоминания есть, а вызовов нет — это
баг разбора разметки; если упоминаний нет — модель не вывела блок.

## 19.09.2026 — wishlist3, часть 2: batch, память, метрики, логи, read_around

**Главное:** третий список закрыт почти целиком. Инструментов стало **40** (было 33),

Новые инструменты:
- `batch { calls: [{ tool, args }] }` — до 50 инструментов за один round-trip, результаты в том же
  порядке. `stopOnError: true` — остановиться на первой ошибке; по умолчанию ошибка одного вызова
  не мешает остальным, в ответе `failed` и `{ ok: false, error }` на своём месте. `batch` внутри
  `batch` запрещён (`EBATCHNEST`). Каждый под-вызов считается в `usage_stats` сам по себе.
- `remember` / `recall` / `forget` — память модели между сессиями в `~/.dsbridge/memory.json`.
  `ttl` в секундах, поиск по `pattern`, лимит 500 ключей, просроченное вычищается при чтении
  (`expiredRemoved`), `forget { all: true }` стирает всё.
- `usage_stats { sort, limit, reset }` — по каждому инструменту `calls` / `errors` / `totalMs` /
  `avgMs` / `maxMs` / `lastAt`, плюс `totals` и `uptimeSec`.
- `process_logs { pid|name, tail, since, waitMs, clear }` — вывод фоновых процессов. `since`
  принимает `nextOffset` из прошлого ответа (число для `stdout` или объект `{ stdout, stderr }`),
  `waitMs` — аналог `tail -f` (до 30 с), `clear` чистит буфер. Если буфер обрезался сверху —
  честный флаг `truncated: true` и сброс курсора, а не молчаливая пустота.
- `read_around { path, pattern, before, after, hit }` — широкий кусок файла вокруг вхождения:
  `matches` (сколько всего), `matchesAt` (номера строк), окно по 20 строк по умолчанию (до 500).

Внутри:
- `runTool` разделён на `runToolInner` (switch) и обёртку с таймингом — метрики пишутся в одном
  месте, а не в каждом `case`.

## 19.09.2026 — exe-сборка: бандлер и самопроверка

**Главное:** `dsbridge.exe` не запускался вообще. `build.mjs` клал в SEA-блоб `src/server.mjs`
как есть, а SEA исполняет главный скрипт как **CommonJS** — падение на первой же строке
(`SyntaxError: Cannot use import statement outside a module`). Плюс exe читал `public/index.html`
и `scripts/screenshot.ps1` с диска рядом с собой, то есть вне проекта не работал.

Что сделано:

- `bridge/build.mjs` — свой мини-бандлер ESM→CJS (~80 строк): `import ... from`, побочные
  `import '...'`, `export const|let|var|function|class`, `import.meta.url` → `__importMetaUrl`.
  На неподдерживаемом экспорте падает с ошибкой, а не собирает молча сломанный файл.
- `bridge/src/assets.mjs` — новый модуль: единственное место, где код знает о файлах проекта
  (`getIndexHtml()`, `screenshotScriptPath()`). В exe-режиме сборка подменяет его исходник
  целиком: html вшит строкой, а `screenshot.ps1` распаковывается в `os.tmpdir()` при первом
  обращении (его нельзя вшить — он запускается как файл).
- `bridge/src/server.mjs` — `PUBLIC_DIR` убран, UI отдаётся через `getIndexHtml()`.
- `bridge/src/tools.mjs` — `SCRIPTS_DIR` убран, `list_windows` / `screenshot` берут путь
  через `screenshotScriptPath()`.
- `bridge/build.mjs` — шаг «4/4»: сборка сама проверяет результат. Копирует exe в чистую
  временную папку, запускает без файлов проекта и дёргает `/api/health`, `GET /`
  (вшитый html + подстановка токена), `write_file`/`read_file`, `sysinfo`, `list_windows`
  (то есть вшитый `screenshot.ps1`). Провал — сборка падает с кодом 1. Флаг `--no-verify`.
  `EBUSY` при копировании node.exe переводится в понятное «закрой запущенный dsbridge.exe».

Проверено: `bridge/test.mjs` — 151 ok / 0 fail, `extension/test.mjs` — 34 ok / 0 fail,
`node build.mjs` — зелёная самопроверка (`health`, UI, write/read, sysinfo, `list_windows`
на 7 окнах). Итог — `bridge/dist/dsbridge.exe`, 83,3 МБ, работает из папки без исходников.

**Важно:** встроенная проверка не зря — она дважды поймала реальные ошибки (подменённый
`assets.mjs` вставлялся в бандл как ESM, минуя трансформер; и исключённый из карты модулей
`assets.mjs` уронил бы `__require`). Обе нашлись только на запущенном exe.

**Не сделано:** `dist/Дипсик-Мост.zip` (собран 17:34) содержит **старые** исходники — в нём
нет `src/assets.mjs` и прежний сломанный `build.mjs`. Архив не пересобирался: релизы Brick
публикует сам. Если он уйдёт наружу в таком виде — у получателя exe не соберётся.
