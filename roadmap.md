# Roadmap: что добавить в «Дипсик Мост»

Источник — `wishlist2.txt` (написала сама модель после закрытия первого списка) плюс
наблюдения по ходу разработки. Оценка объёма: **S** — меньше вечера, **M** — вечер-два,
**L** — несколько дней.

Правило проекта: одна фича — одна запись в журнале версий, тесты расширяются вместе с кодом,
после правки `content.js` расширение перезагружается вручную (`chrome://extensions` → ⟳).

---

## Приоритет 1 — быстрые победы

Низкий риск, изолированы внутри моста, окупаются сразу.

### 1.1. `edit_many { path, edits: [{ old, new, replace_all? }] }` — M ✅ СДЕЛАНО

Самый востребованный пункт. Сейчас модель, чтобы поправить 5 мест в файле, делает 5 вызовов
`edit_file`. Каждый — отдельный round-trip через чат, отдельная пачка «Слишком частые сообщения».
Один вызов с массивом правок решает это.

Реализовано 19.09.2026 — 29-й инструмент, добавила сама модель через мост, тесты расширены.
Семантика та, что и планировалась (последовательные правки, `atomic`, `failures`), см. README.

- Семантика: правки применяются **последовательно** к текущему состоянию текста. Если одна
  не нашлась — по умолчанию откат всего (атомарно), либо `atomic: false` для применения
  успешных. Возврат — сколько применилось, какие не нашлись.
- Валидация: пустые `old`, `old === new`, дубликаты позиций — `EARGS`.
- Тесты: последовательные правки, откат при `ENOMATCH`, `replace_all` в составе пакета.

### 1.2. `diff { pathA, pathB }` и `diff_git { path, rev }` — S

- `diff` — текстовое сравнение двух файлов в рабочей папке, unified-формат.
- `diff_git` — `git diff <rev> -- <path>` через `runProcess` (argv, без шелла — как `git`).
- Обе читающие, флаги не нужны.
- Тесты: идентичные файлы, разные, отсутствующий.

### 1.3. Опции `screenshot`: `selector`, `fullPage`, `dark` — M

Расширяют уже готовый `browser.mjs`, не тянут новых зависимостей.

- `selector` — снять конкретный элемент (`element.screenshot` через CDP или клип-область).
- `fullPage` — вся высота, а не вьюпорт.
- `dark` — эмуляция `prefers-color-scheme: dark` (флаг Chrome `--force-dark-mode` +
  `--enable-features=WebContentsForceDark`).
- `device` — эмуляция мобильного (viewport + user-agent). Отдельно от `width/height`.
- Тесты: локальный html с высоким блоком (fullPage даёт выше картинку, чем вьюпорт),
  селектор на цветном div (пиксель в центре совпадает с заданным цветом).

### 1.4. `process_logs { pid|name, tail, follow }` — M

`list_processes` отдаёт хвост 4 КБ статикой. Для «запустил сервер, посмотри логи» этого мало.

- `follow: false` — просто хвост (как сейчас).
- `follow: true` — ждать до `timeoutMs`, собирая новый вывод, и вернуть его одним куском
  (не настоящий stream через чат — расширение такой формат не поддержит).
- Плюс `clear: true` — очистить буфер, чтобы `follow` не тянул старое.
- Тесты: процесс, печатающий раз в 200 мс; проверка, что `follow` вернул только новое.

## Приоритет 2 — большие, но ценные

### 2.1. Интерактивный браузер: `browser_open / navigate / click / type / eval / dom / close` — L

**Самая крупная задача во всём списке.** Сессия headless-Chrome живёт между вызовами:
одна вкладка, один WebSocket к DevTools Protocol, команды поверх него.

- `browser_open { url, headless? }` — поднять сессию, вернуть `sessionId`.
- `navigate { sessionId, url }`, `click { sessionId, selector }`,
  `type { sessionId, selector, text }`, `eval { sessionId, expression }`,
  `dom { sessionId, selector }` — вернуть outerHTML/текст.
- `browser_close { sessionId }` — обязательный, иначе Chrome останется висеть.
- Всё за `allowCommands` (это исполнение кода на странице). `http(s)` — ещё и за `allowNetwork`.
- **Риск:** без Puppeteer придётся руками писать CDP-клиент (framing, события, target-сессии).
  Если уходить в зависимости — это меняет принцип проекта «только stdlib». Решение принимать
  отдельно: держать stdlib и написать ~300 строк CDP-обвязки, либо поставить одну зависимость
  (`chrome-remote-interface`) и получить функциональность за вечер.
- Тесты: локальный html с кнопкой и полем; проверка, что click/type/eval дают ожидаемый DOM.

### 2.2. `remember` / `recall` — M

Память между сессиями, чтобы модель не теряла контекст проекта.

- `remember { key, value }` / `recall { key }` / `recall {}` (всё) / `forget { key }`.
- Хранение — `<workspace>/.dsbridge-memory.json`, простой ключ-значение + `updatedAt`.
- Безопасность: тот же path jail, значение обрезается до разумного размера (напр. 64 КБ).
- **Открытый вопрос:** должен ли `remember` сразу писать в `INSTRUCTION` (т.е. попадать в
  контекст следующего чата автоматически), или модель вызывает `recall` сама, когда сочтёт
  нужным. Первое удобнее, второе предсказуемее. Склоняюсь к первому — но это надо решить
  до реализации.

### 2.3. `image_info { path }` — S (вместо `ocr`/`image_diff`)

Модель просила `image_info` / `image_diff` / `ocr`. OCR — это зависимость (tesseract),
против stdlib. `image_diff` — нишевая.

Что реально можно сделать без зависимостей: `image_info` — размер, формат, EXIF (если png/jpeg
с метаданными), средняя яркость, доминирующий цвет. Полезно, когда модель не «видит» картинку
(например, `allowNetwork` выключен и внешний источник недоступен).

- Тесты: png 1×1, png 100×100 заданного цвета — проверить размеры и доминирующий цвет.
- `image_diff` и `ocr` — **отложить до явной необходимости**, зафиксировать в бэклоге.

## Приоритет 3 — отложено сознательно

### 3.1. Прямой захват stdout от `.exe` в PowerShell

Известная шероховатость PowerShell 5.1 (`CantActivateDocumentInPipeline` при чтении stderr java).
Обход существует (`cmd /c`, `2>&1 | Out-String`) и уже описан в README. Пока не мешает —
трогать не стоит. Вернуться, если появится реальный кейс, где обход не срабатывает.

### 3.2. Нативный webview вместо браузера для UI моста

Один exe сейчас открывает UI в системном браузере. Это неудобно, но работает. Переход на
нативный webview (Tauri/Electron) — отдельный большой проект, не в этот цикл.

## Отдельный трек: живой чат DeepSeek

**Главный риск проекта** (см. `plan.md` п. 9.1) — парсинг DOM `chat.deepseek.com` и вставка
в React-поле не проверены на живом сайте. Все правки `content.js` до сих пор шли «по коду».

Что делать:

1. Открыть реальный чат с загруженным расширением, посмотреть строку диагностики
   («блоков на странице: N · вызовов: M»).
2. Кнопкой «DOM» посмотреть, что расширение видит как кандидатов.
3. Проверить отправку: не ломается ли React-поле, доходит ли сообщение.
4. По результату — либо всё ок, либо точечно править селекторы.

Это не «фича», но именно здесь текущая версия скорее всего требует работы.
